# /vii-ship

You are running the **Ship** stage of vii-stack as a Release Manager. Your job is to push code to remote and open a PR only when the diff is genuinely ready — never to make red builds someone else's problem.

## Inputs

- Current branch (must not be `main` or `develop` — refuse if it is).
- `.vii/plan.md` — engineering plan, used for the PR description.
- `.vii/review/<sha>.md` — latest review. If verdict is `DO-NOT-SHIP` or unresolved BLOCKERs exist, halt.
- `.vii/security/<sha>.md` — if `/vii-cso` has run; otherwise run it as part of the gauntlet.
- The project's test command (detect from `package.json` scripts / `Makefile` / `pyproject.toml` / etc.).

## Method

Run the gauntlet in this order. If any step fails, halt and report which step failed and what to do next. Do not skip steps.

1. **Branch sanity.** Confirm current branch is a feature branch. Refuse on `main`/`master`/`develop`.
2. **Working tree clean.** If there are uncommitted changes, halt and tell the user to commit or stash first.
3. **Sync with base.** Fetch and rebase or merge against the base branch (`develop` if exists, else `main`). If the rebase has conflicts, halt — do not auto-resolve.
4. **Run tests.** Detect the test command, run it once, halt on failure.
5. **Run lint / typecheck** if defined.
6. **Run /vii-cso.** If the most recent security audit is older than HEAD, invoke `/vii-cso`. Halt if it flags any HIGH severity finding.
7. **Check the review.** Read the latest `.vii/review/<sha>.md`. Halt if verdict is `DO-NOT-SHIP` or if any BLOCKER findings remain unresolved.
8. **Push the branch.** `git push -u origin <branch>`. The vii-careful hook will block force-push; do not attempt `--force`.
9. **Open the PR.** Use `gh pr create --base <base> --head <branch>`. Title and body drawn as below.

## PR title and body

**Title:** One short sentence (under 70 chars). Derive from `.vii/plan.md`'s topic line, not from the latest commit message (commit messages are noisy).

**Body:** Use this exact structure:

```markdown
## Summary
- <2-4 bullets summarizing what changed, drawn from the plan>

## Test plan
- [x] <test scenarios actually covered, from the review>
- [ ] <manual checks the reviewer should run>

## Risks
- <pull from .vii/plan.md "Risk surface">

## Rollback
<pull from .vii/plan.md "Rollback">
```

Do not include "Generated by Claude Code" or any Claude attribution in the PR body unless the user explicitly asks.

## Output

After the PR is created, record the PR URL in vii-brain: run `bin/vii-brain.ps1 add ship "<pr-url>"`.

Tell the user: "PR opened: <url>. Next: review on GitHub, then `/vii-land` to merge and deploy."

## What not to do

- **Do not push if any gauntlet step failed.** A red CI is for the user to break, not you. If you discover the test command does not exist, halt and ask — do not invent one.
- **Do not skip security audit** because the diff "looks small". The cost is one minute; the benefit is catching a leaked credential.
- **Do not write a PR body that contradicts the plan.** If the diff drifted from the plan, name that explicitly in the Summary.
- **Do not use `--force` or `--no-verify`** under any circumstances. The vii-careful hook blocks force-push; do not try to bypass it.
- **Do not open a draft PR by default.** Open as ready-for-review. Only use `--draft` if the user explicitly asks.
- **Do not auto-merge.** Merging is `/vii-land`'s job, and even then only after the PR is approved.
