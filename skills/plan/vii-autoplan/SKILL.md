# /vii-autoplan

You are running the full **Plan** stage of vii-stack. Your job is to orchestrate the right planning perspectives for this specific brief and produce a single complete `.vii/plan.md` that the Build stage can execute without further questions.

## Inputs

- `.vii/think/*.md` — the brief from `/vii-office-hours`. If none exists, halt and tell the user to run `/vii-office-hours` first.
- Current repo state — same survey as `/vii-plan-eng`.

## Method

### Step 1 — Classify the work

Read the brief. Classify the change into one or more of these buckets:

| Bucket | Signals |
|---|---|
| **Backend / API** | new endpoints, data models, background jobs, migrations, auth |
| **Frontend / UI** | new screens, components, interactions, visual changes |
| **CLI / tooling** | new commands, config keys, scripts, developer-facing APIs |
| **Infrastructure** | deployment, CI, env vars, secrets, scaling |
| **Data / ML** | pipelines, schemas, model changes, analytics |

State the classification in one line before planning.

### Step 2 — Select perspectives

Always run **Engineering** (`/vii-plan-eng`). Then:

| If the work involves… | Also run… |
|---|---|
| Any user-facing value or priority tradeoff | **CEO** (`/vii-plan-ceo`) |
| Any UI surface, component, or visual change | **Design** (`/vii-plan-design`) |
| Any new developer-facing API, CLI flag, config, or error surface | **DevEx** (`/vii-plan-devex`) |

If the brief is purely infrastructure or data with no user or developer API surface, Engineering alone is sufficient — state why you skipped the others.

### Step 3 — Run each perspective in order

Run the perspectives in this order: **Engineering → CEO → Design → DevEx**. Each appends its section to `.vii/plan.md`. Do not skip ahead.

For each perspective:
- Follow that skill's Method exactly (do not abbreviate).
- If that perspective finds a blocker (CEO: NO-GO; Design: design blocker; DevEx: API blocker), halt and surface it to the user before continuing. Do not proceed past a blocker silently.

### Step 4 — Write the summary header

After all perspectives are written, prepend (or overwrite the top of `.vii/plan.md`) with a summary block:

```markdown
# Plan: <topic>

_Generated by /vii-autoplan on <YYYY-MM-DD>. Perspectives: <list>. Brief: .vii/think/<slug>.md._

## Quick summary
- **What:** <one sentence>
- **Why:** <success metric from brief>
- **Perspectives included:** <Engineering / CEO / Design / DevEx>
- **Blockers:** <none, or list>
- **Next step:** implement, then `/vii-review`
```

## Output

A single `.vii/plan.md` containing the summary header followed by all selected perspective sections in order.

Tell the user: "Plan complete (`/vii-autoplan`). Perspectives: <list>. Next: implement, then `/vii-review`."

## What not to do

- **Do not skip Engineering.** It is always required — it is the spine that the other sections annotate.
- **Do not run Design on a pure backend change** or DevEx on a pure visual change. The classifier exists so the plan stays relevant, not exhaustive.
- **Do not proceed past a blocker** without surfacing it. A CEO NO-GO means planning stops; the user decides whether to reframe the brief or kill the work.
- **Do not write code.** This is still plan-stage. If the user asks for an implementation, point them to start building once the plan is approved.
- **Do not merge or summarize** the perspective sections into each other. Each section is owned by its skill and should stand independently.
